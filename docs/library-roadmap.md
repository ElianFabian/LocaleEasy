# LocaleEasy library roadmap

LocaleEasy provides an app-owned, ordered language preference for a single Android process, observable from Kotlin, with localized resources and automatic refresh for activities that wrap their base context. The host owns navigation, user input, and any text it caches. The experiments below record the original implementation decisions.

The implementation now exports coroutines core, normalizes preferences during selection and restore, applies a locale-only context override, and serializes changes around one `state` flow. It also preserves independent platform settings and restricts WebView repair to application resources. The table below retains the original sequence and its remaining acceptance checks. [Verification report](locale-verification.md)

## What changed the priorities

The following probes used the public API of the unchanged library in a separate sample package on an Android 7.0 / API 24 x86 emulator. The starting system language was English (US). Each cold-start observation used a fresh process with the prior process's preferences.

| Probe | Observed result |
| --- | --- |
| Call `setLocales(listOf(Locale.FRENCH, Locale.FRENCH))` | The setter threw `IllegalArgumentException: list[1] is a repetition`. Preference and effective locales already contained both entries, storage held `fr,fr`, and application resources still reported `en-US`. |
| Allow that preference write to finish, then start another process | AndroidX Startup crashed before the test body. The cause was the same exception from `LocaleList` in `AndroidLocaleEasy.updateResources()` during initialization. |
| Call `setLocale(Locale("fr-CA"))`, then restart | Android accepted this single-argument language constructor. Its tag serialized as `und`, which LocaleEasy stored. On restart LocaleEasy recovered to `FollowSystem`. The intended French Canadian locale can be constructed with `Locale.forLanguageTag("fr-CA")`. |
| On the main thread, collect `preference` with `Dispatchers.Main.immediate`. When French arrives, call `setLocale(Locale.ITALIAN)` from the collector. Start the sequence by selecting French. | After both setters returned, preference and storage said Italian. The effective list and application resources said French. Calling the Italian setter again returned early and left the disagreement intact. |

These are separate implementation defects. In the duplicate case, `setPreference()` persists and publishes a value before constructing the platform locale list. Android 7 and Android 9 explicitly throw for repeated entries. The installed API 37 SDK source drops repeats, so recent-device tests can hide the failure. In the collector case, `publish()` sets the preference flow, the collector performs a complete nested update, then the outer call resumes and writes its older effective locales. Sequential rapid-tap tests exercise a different ordering. ## Implementation order

The steps progress from small, independently testable fixes to changes that span lifecycle and resource behavior. Steps 1–4 are release blockers. Steps 1 and 2 fit in a first patch.

| Step | Change and reason | Acceptance check | Manual verification |
| --- | --- | --- | --- |
| 1. Export the reactive API dependency | Declare coroutines core as an `api` dependency. The existing minimal consumer could only read `effectiveLocales.value` after this change. The sample's own dependencies mask the issue. | Assemble a consumer that depends only on LocaleEasy and reads or collects a flow. Repeat against the release artifact and its dependency metadata when publication is configured. | No |
| 2. Validate and migrate ordered locales | Normalize exact repeats to their first occurrence before equality checks, persistence, or platform calls. Apply the same normalization when restoring an existing installation. Validate that each accepted locale has a usable language after conversion to its persisted tag. Preserve legitimate scripts, regions and extensions. | On API 24, submit `[fr, fr, fr-CA]` and expect `[fr, fr-CA]` everywhere. Seed old `fr,fr` storage and launch a fresh process. Submit the malformed language-constructor case and assert failure before any state changes. Round-trip `zh-Hant-TW` and a locale with a Unicode extension. | No |
| 3. Narrow the configuration override | In `localizedContext()`, pass a locale-only delta, including locale-derived layout direction. Set `fontScale = 0f` for an undefined override on older Android. Keep the full configuration copy confined to the legacy resource-update operation. The retained-context Pixel night-mode probe already passed with this isolated change. | Hold a French wrapper across real night-mode and font-scale changes. Compare the base and wrapper qualifiers and read a translated string from the wrapper. Cover API 21 and a recent API. | Automated checks cover the bug. Inspect large text and RTL layout for sample acceptance. |
| 4. Make locale changes coherent under re-entry | Use one immutable internal state containing preference and system locales with derived effective locales. Serialize the full change, including persistence, resource application, publication and refresh scheduling. Queue a nested request and drain it before the outermost update returns. Read one state value when constructing a wrapper. Merely adding a public flow around the current writes would leave the defect in place. | Reproduce French → Italian from an immediate collector. At quiescence assert Italian in the preference, effective list, storage, a fresh localized context, and the inflated activity. Repeat with a nested reset and verify an identical retry requests no additional relaunch. | No |
| 5. Establish ownership of system settings and process defaults | In local mode, startup currently clears any nonempty OS app-language override, even when existing local storage wins and the OS setting came from another owner. The sample advertises that OS picker. Isolate the picker and framework switch in the diagnostic integration. Scope cleanup to a documented migration with evidence of previous ownership. Inventory callers relying on application resources and `Locale.getDefault()` before narrowing those process-wide writes. | Seed local French and an independently set OS Italian. A normal startup should preserve the unrelated setting. Test legacy-owner import and reset separately. Check existing callers' formatter defaults, wrapped strings and app-context strings after a switch and after restart. | Inspect the actual Android Settings entry and sample instructions once. Automate the state assertions. |
| 6. Constrain WebView repair | `fixWebViewLocale()` mutates the application and every tracked activity, including an outgoing activity. In the repeated Pixel test, normal local recreation translated 8/8 switches. Adding the repair gave 5/8, with the wrong string already available to the replacement inflater. Record the WebView provider and the resources it actually changes before choosing a narrower repair or deprecating it. | Repeat French/Spanish switches in one process with and without WebView initialization and repair. Read the actual XML string at inflation and Compose text after restoration. Include a stopped activity. | Check the affected provider/device and navigation state if the documented workaround promises to preserve it. |
| 7. Close the visual and lifecycle coverage gaps | Keep `ActivityCompat.recreate()` for stale participating activities. Treat continuity of a settings sheet as its own UX requirement. First try a sheet drawn in the activity's content tree if continuity is required. Prototype selective in-place rebinding only on a host that owns every affected resource. | Keep a dialog open, type text, change language and compare activity, root and dialog identities, text, cursor, navigation, insets, and frame recordings. Repeat with RTL, a stopped back stack and two visible activities. Test follow-system and a fixed override across a real system-language change. | Yes for visible flashes, sheet movement and toolbar overlap. Automate state, translation and instance counts. |

For step 7, the Pixel already showed a replacement activity, a single new root and restored input using ordinary local recreation. Both forced-factory variants built two roots and lost the editor state. Reopening a saved dialog can preserve the user's place while visibly replacing the dialog window. The fixture that handled a night-mode callback and requested local recreation demonstrated a window-handoff improvement for that specific system change. It supplies no requirement for consumers to intercept night mode. ## Public API and scope

- An explicit choice of English and following an English system produce the same text today and behave differently when the device changes to Spanish. Use `followSystem()`, `setAppLocale(Locale)`, or `setAppLocaleList(List<Locale>)`.
- The sample collects public properties such as `preference`, `effectiveLocaleList` and `systemLocaleList`. Each flow projects from the same internal state. An emission represents an applied selection. A window may draw its first translated frame later.
- **Define resource scope.** On API 21–23, LocaleEasy can keep the full ordered preference in storage but its implementation passes only the first locale to Android resources. From API 24, Android can use the ordered list and resolve individual resources by availability. Show workers and notifications obtaining a fresh localized context when constructing text. A long-lived custom wrapper is bound to the selection used to create it. Document single-process support for now. Remote services would need explicit initialization and interprocess coordination. [Android multilingual resource resolution](https://developer.android.com/guide/topics/resources/multilingual-support) · [SharedPreferences process contract](https://developer.android.com/reference/android/content/SharedPreferences)
- **Choose comparison features by the problem they solve.** Lingver's small setter API and injectable store are useful precedents. Its caller owns already-fetched content. LocaleEasy's added value is observing ordered preferences and refreshing participating screens. AndroidX AppCompat is the reference for a host that specifically wants the Android Settings picker and platform language integration. Akexorcist's archived library shows how to document services and receivers. Localazy solves catalog discovery and translation delivery. For the sample, use one host-owned supported-language list and verify the chosen translation is packaged or installed. A translation service, custom persistence, and a refresh-strategy interface can wait for concrete consumers.
